# AGENTS.md

Read this file first, before doing anything in this repository.

**Camellia** is CJ Huang's design system. It has one authored DTCG token file, which generates CSS custom properties and syncs one way into Figma variables and styles through a local Figma plugin. CJ is a product designer (UI/UX) learning design engineering. Explain meaningful decisions and unfamiliar concepts; summarize routine commands and checks.

## Protection of this file

**No agent may edit, replace, delete, rename, move, or indirectly regenerate this file without CJ's explicit permission for that specific proposed change.**

- General permission to "edit the docs", "clean up the repo", or "proceed" doesn't count.
- To propose a change, show CJ the exact diff and the reason, then wait.
- Don't work around this rule: no competing instruction files, tool configuration, generated rules, or alternative onboarding files. Don't modify or disable the guardrails that back it without CJ's permission: `.github/workflows/agents-md-approval.yml`, `.github/scripts/check-agents-md-approval.sh`.
- A CI approval check backs this policy, but it has gaps (see [guardrails](docs/verification.md#agentsmd-protection)). Nothing blocks a local edit, so the policy itself is the local protection. CJ applies approved changes; agents never edit this file themselves.
- Only CJ resolves a failed approval check. Agents must never post the `/approve-agents-md` comment, re-run the check to get around it, or change it.

## Authorization and autonomy

Begin work when CJ explicitly requests a task. That request authorizes the routine actions necessary to complete it within its stated scope, subject to the protected actions below.

Do not ask CJ to approve each implementation step. Do not interpret permission for one task as permission to start unrelated work or the next roadmap phase.

| You may do independently within an approved task | You need CJ’s explicit permission |
|---|---|
| Read files, inspect the repository, and run relevant commands | Start the next roadmap phase or expand the approved scope |
| Create and edit implementation files, tests, and relevant documentation, excluding AGENTS.md | Edit, replace, delete, rename, or indirectly regenerate AGENTS.md |
| Make routine implementation choices, including naming, internal structure, and test organization | Change the approved roadmap, canonical token source, sync direction, or canonical schema |
| Choose between reasonable implementation options using established conventions; explain meaningful tradeoffs afterward | Change public contracts, including token names, CSS variable names, Figma names, or plugin commands |
| Fix defects introduced by your work and rerun verification | Add dependencies, install packages, or change package manifests and lockfiles |
| Run existing builds, tests, lint, and generation scripts; inspect their outputs | Commit, push, open a PR, merge, publish, or deploy, unless CJ’s task explicitly authorizes that action (see [pstack](#pstack) for its PR exception) |
| Update implementation status and the feature map to reflect verified work | Write to Figma or execute Plugin API operations against a Figma file, unless the approved task explicitly includes those operations |
| Report blockers and propose changes outside your scope | Delete or overwrite unrelated work, discard uncommitted changes, or perform destructive Git operations |
| | Change or disable the guardrails for this file (listed under [Protection of this file](#protection-of-this-file)) |

### Apply permission at the correct scope

An explicit request such as “open a PR for this change” authorizes that action for this task. Do not ask again unless the intended action materially changes.

A task requiring protected actions must include explicit authorization for those actions. Otherwise, complete the independent work available and explain the specific permission needed.

### Handle choices and uncertainty

Make routine, reversible implementation choices independently when they preserve approved behavior and contracts.

Ask CJ when a decision changes intended behavior, project direction, protected contracts, or requires permission listed above. Present the options, tradeoffs, and your recommendation.

Investigate facts you can establish from the repository or by running checks before asking CJ.

### Completion and phase boundaries

Complete the approved task and its relevant verification. Report what changed, the evidence obtained, and anything unverified.

Stop at the end of the approved scope. Identify the next task without beginning it automatically.

Never weaken checks, alter acceptance criteria, or bypass permission restrictions to declare completion.

## Engineering rules

- **Keep it simple.** Use conventional structure, explicit domain types, validated boundaries and narrow APIs. Don't add clever abstractions.
- **Keep the DTCG file canonical.** Bridge differences between DTCG and Figma with adapters in the plugin, not with Figma-specific fields in the schema.
- **Write no explanatory code comments by default.** Do keep legal notices and tooling directives. Keep a short comment only for an essential external constraint that the code can't show (e.g. a Figma API quirk). Existing comments stay as they are; there is no repo-wide cleanup unless CJ asks.
- **When you find an anti-pattern, address recurrence.** Choose the most appropriate sustainable mechanism: architecture, types, schema validation, an existing lint rule, a regression test, runtime verification, or written guidance. Balance effectiveness, false positives, ease of use for agents, maintenance, and cost rather than applying a rigid ranking. Within an approved task, add focused regression tests or configure existing lint rules when they preserve intended behavior and public contracts. Get CJ's approval before architectural changes, adding dependencies, changing protected contracts, or expanding scope. Don't write custom lint rules for subjective preferences. Report the mechanism added and the failure it addresses.
- **Commit messages** use [Conventional Commits](https://www.conventionalcommits.org/), e.g. `docs: add agent onboarding guides` or `feat(figma): sync semantic variables`.

## Implementing and verifying

- The implementer runs the relevant checks before handing off.
- For substantive changes, a **separate verifier** reviews the diff against the acceptance criteria, runs the checks, and exercises the behavior (see [verification](docs/verification.md#implementverify-handoff)). Fixes go back to the implementer. The verifier never weakens criteria or tests.
- Trivial changes (typos, wording) may skip independent review. Say explicitly that you skipped it.

## Reporting evidence

Every completion report states:

1. the revision (commit hash, plus whether there are uncommitted changes);
2. the commands you ran and their actual results;
3. any runtime evidence;
4. what was **not** verified.

- Label each claim as **observed** (you saw it), **inferred**, or **unknown**.
- **Never claim Figma behavior from tests against the fake Figma or from compilation.** Only a run in Figma verifies Figma behavior.
- When blocked, stop and report what you tried, what you observed, and the options. Don't improvise around the blocker.

## pstack

[pstack](https://cursor.com/marketplace/cursor/pstack) is a Cursor plugin CJ uses (install with `/add-plugin pstack`, then `/setup-pstack`). As of 2026-10-16 it is **not installed**; check before claiming any pstack workflow ran. Where pstack and this file differ, this file and the roadmap win:

- **Autonomy inside the task, CJ at the boundaries.** pstack's "never block on the human" applies within an approved task. Protected actions and phase boundaries still wait for CJ.
- **PRs.** At the end of an approved, verified task, a pstack playbook may commit to the task branch, push it, open the PR, and run autopilot on it to fix CI and review comments. It never merges; CJ merges. No shipping, orchestrated merges or overnight runs unless CJ asks.
- **State the plan before implementing.** If CJ has already approved the task, proceed within that scope without requesting approval again. Pause only when the plan requires expanding scope or taking an action that needs CJ's explicit permission.
- **Review.** One separate verifier by default. Use a review panel (`/interrogate`, `/arena`, `/swarm`) or other additional agents only when CJ asks, or when an agent proposes one for a risky decision with a concrete benefit and CJ agrees.
- **Models.** `/setup-pstack`'s model routing is accepted. It doesn't override anything in this file.
- **One feature map.** The map is pstack's verification-skill layout at [.cursor/skills/verify-camellia/](.cursor/skills/verify-camellia/SKILL.md). `/create-verification-skill` and `/maintain-verification-skill` must update it, not create a second skill or map.
